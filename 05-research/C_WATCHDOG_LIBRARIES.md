# Track C — Dedicated Watchdog/Loop-Detection Libraries for LLM Agents

**Research date:** 2026-08-19
**Question:** Does a ready-made, pip/npm-installable watchdog exist that CENTRAL could drop in for CARL, instead of hand-rolling it?
**Method:** WebSearch + WebFetch + direct GitHub API queries (`gh api repos/...`) for verified stars/last-push dates — not just marketing copy.

---

## Bottom line up front

**No single ready-made tool does what CARL needs to do out of the box.** The space splits cleanly into two piles:

1. **Full observability platforms** (Langfuse, Helicone, Phoenix, LangKit) that give you *traces and dashboards a human watches*, plus in some cases a generic threshold-alert engine (latency/cost/error-rate). None of them ship an agent-loop or reasoning-degradation detector that fires automatically out of the box — you'd wire your own custom evaluator/score into their pipeline, which is most of the work of hand-rolling CARL anyway, just hosted inside someone else's SaaS trace schema.
2. **Small, single-purpose loop-detector libraries** that genuinely do close to what CARL needs, built by solo developers in the last ~6 months. One is a strong fit: **`loopgain`** (pip-installable, ships a `ClaudeAgentSDKAdapter`, 124 GitHub stars, last commit 2 days before this research). A second, **`contextrot`**, is a well-built, actively maintained (52 stars, last commit 2 days ago) statistical degradation analyzer built specifically for Claude Code sessions — but it's a **post-hoc transcript analyzer**, not a real-time watchdog, so it answers a different question than CARL needs answered live.

Neither is a magic drop-in replacement for CARL. `loopgain` requires CARL to define its own "error signal" function per subprocess (same design burden as hand-rolling a check), and its Claude Agent SDK adapter assumes you're driving the SDK's `query()` loop directly rather than supervising an independently-spawned headless subprocess from outside — CENTRAL's actual architecture. `contextrot` would need to be re-pointed at live JSONL transcripts on a poll loop to serve as a watchdog rather than a retrospective report.

**Recommendation in one line:** fork the *detection primitives* (measurable signals: repeated tool-call fingerprints, error-count trajectories, zero-reasoning-token turns, context-fill correlation) from `loopgain` + `contextrot` + the pattern used by Nous Research's Hermes Agent (`tool_guardrails.py`) rather than either full library — but this is "reuse the recipe," not "install the package," so it does not fully satisfy the project's "don't reinvent" bar. See recommendation section at the end for the honest tradeoff.

Adopting any of them to get loop detection means writing the same detection logic CARL would need anyway, just inside a heavier host (extra infra dependency, extra vendor surface, extra latency) for the win of getting a nice UI you probably don't need for an internal supervisor process.

## 3. Chroma's "Context Rot" research

**`chroma-core/context-rot`** — confirmed via `gh api`: 299 stars, 35 forks, MIT license, **last commit pushed 2025-09-03** (~11.5 months before this research date; the `updated_at` timestamp of 2026-08-19 reflects people starring/watching it, not new commits).

Read the actual repo contents: it is **purely an academic replication toolkit** — per-experiment folders (Needle-in-a-Haystack extension, LongMemEval, Repeated-Words synthetic task), a downloadable dataset, a results folder, and per-experiment READMEs with instructions to reproduce the paper's benchmark numbers against GPT-4.1/Claude 4/Gemini 2.5/Qwen3 using your own API keys. **There is no detection tool, no installable library, no live-monitoring code artifact.** Chroma shipped a finding, not a product. Do not expect to `pip install` anything from this org for this purpose.

A community project inspired by the same research **does** ship a real tool — see `contextrot` (Priyanshu-byte-coder) in §5, which is unaffiliated with Chroma but operationalizes the same idea for Claude Code sessions specifically.

## 4. Anthropic's own tooling

Checked the live Claude Agent SDK hooks reference (`code.claude.com/docs/en/agent-sdk/hooks`) directly — full current hook-event table, ~30 events. Every single one is a **structural/lifecycle trigger**: `PreToolUse`, `PostToolUse`, `PostToolUseFailure`, `PostToolBatch`, `UserPromptSubmit`, `Stop`, `StopFailure`, `SubagentStart`, `SubagentStop`, `PreCompact`, `PostCompact`, `PermissionRequest`/`Denied`, `SessionStart`/`End`, `Notification`, `TaskCreated`/`Completed`, `ConfigChange`, `FileChanged`, etc.

**Confirmed: none of them fire on output quality, semantic repetition, or reasoning degradation.** `PreCompact`/`PostCompact` — the two the parent project had already found — trigger purely on the conversation hitting a token-count threshold for context compaction, exactly as suspected; there is no sibling hook that fires on quality decay. The SDK docs even flag the closest adjacent failure mode — a `UserPromptSubmit` hook that spawns subagents which re-trigger the same hook — as a **known infinite-loop risk the developer must guard against themselves** ("Recursive hook loops with subagents" in the troubleshooting section), which is itself evidence Anthropic has not built an automatic backstop for this class of problem at the SDK level.

Checked `anthropics/anthropic-cookbook` (51,864 stars, pushed 2026-08-19) — no dedicated loop-detection or degradation-detection recipe found in search; the cookbook's agent-pattern recipes cover orchestration/prompting patterns, not supervisory monitoring. `anthropics/claude-agent-sdk-python` (7,935 stars, pushed 2026-08-19) is the SDK itself, actively maintained, but is the same hooks surface described above — no separate degradation-detection module.

**Verdict:** confirmed — nothing at the SDK or cookbook level beyond what the parent project already found. CARL genuinely has to be built on top of raw token/tool-call/message events; Anthropic provides the event stream, not the judgment layer.

## Recommendation

**Nothing found is a clean, install-and-forget replacement for CARL.** The honest options, in order of preference:

1. **Best real option if CENTRAL wants to try adoption first:** pull in `loopgain` (`pip install loopgain`) for the narrow slice of CARL's job that is "detect convergence/divergence of an iterative correction loop using a numeric error signal," since it already ships a Claude Agent SDK adapter and is the most actively maintained, most-starred dedicated candidate found (124 stars, pushed 2 days before this research). It will **not** cover CARL's other jobs — tool-call repetition fingerprinting, context-fill correlation, zero-reasoning-token turns — because those aren't what it measures.
2. **Best real option for context-rot specifically:** `contextrot` is a legitimate, actively maintained, Claude-Code-native tool for the "is this agent's output quality falling off as context fills" question — but it reads finished/growing transcript files after the fact, so CARL would need to poll it or reimplement its statistical method (edit-failure rate, retry-loop rate, re-read rate, self-correction rate vs. context-fill %, Wilson CI) directly against live JSONL rather than shelling out to the CLI mid-session.
3. **For the tool-call-repetition piece specifically** (the single most common trigger across every candidate found — `loopgain`, `contextrot`, `opencode-anti-loop`, `AgentCircuit`, `tool-loop-break`, and Hermes Agent's `tool_guardrails.py` all independently converge on the same idea): fingerprint `(tool_name, canonicalized_args)`, or `(tool_name, canonicalized_args, result_hash)` per the known gap flagged in Hermes Agent's own issue tracker (args vary but result never changes), count occurrences in a sliding window, and trip a threshold. This is maybe 40 lines of code and every "real" project in this space has independently reinvented it — which is itself the strongest signal that this primitive is *supposed* to be hand-rolled per-host, not imported.

**If forced to pick one sentence:** there is no dedicated, mature, widely-adopted watchdog library to fork wholesale; the two closest candidates (`loopgain`, `contextrot`) are real, live, and worth reading the source of or trialing for a narrow slice each, but CARL's core logic — tool-call-repetition fingerprinting driving a live supervisor over externally-spawned headless subprocesses — still has to be hand-rolled, because every project that does something similar (including the one true production-scale example, Hermes Agent) does it as an embedded piece of its own framework, not as a standalone importable watchdog.
